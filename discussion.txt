Gemini's critique for the code:
===============================
This is a highly structured, well-thought-out implementation. Using a hash-consed DAG to intrinsically handle $\mathbb{F}_2$ cancellations
(like $e \oplus e = 0$) and structural hashing is the exact right approach for verification. 

However, since you mentioned the worst-case scenario—evaluating probes exponentially many times relative to the number of wires
(the $2^w$ problem)—the performance landscape changes drastically. When an operation runs millions of times, minor overheads compound into
complete blockages. 

Here is a candid review of the algorithmic and memory bottlenecks currently in your architecture, ranked by severity.


### 1. The "Per-Probe" Factoring Trap (Critical Time Leak)

Currently, `initProbe` calls `gdag.dag.factor origRoots`. This means you are dynamically running the factoring algorithm *inside* the
exponential probe loop. 

**The Problem:** Factoring involves deep DAG traversals, frequency counting, and interning new nodes. Doing this repeatedly for the exact
same circuit sub-graphs across different probe combinations is a massive duplication of work. 

**The Fix:** Circuit factoring should be a **static, one-time preprocessing step**. You should factor the `GlobalDAG` *before* you generate
the power set of probes, effectively locking the DAG into a canonical, optimized shape. The probes should then just evaluate on this
static, factored DAG.


### 2. Dense Arrays vs. HashMaps (Critical Time & Memory Leak)

Your `DFSState` and `ProbeState` heavily rely on `Std.Data.HashMap NodeId Nat` for `xorParCount`, `totalParCount`, and `parents`.

**The Problem:** HashMaps are great for sparse, arbitrary keys. But your `NodeId` is explicitly defined as `Nat` and increments linearly
(`nextId := id + 1`). This means your IDs are perfectly dense and contiguous. Allocating, hashing, and traversing HashMaps inside an
exponential loop is incredibly slow and fragments memory.

**The Fix:** Replace `HashMap NodeId X` in your probe state with dense `Array X`, where the index *is* the `NodeId`. Array lookups/updates
are $\mathcal{O}(1)$ pointer offsets. For a graph of 10,000 nodes, pre-allocating an `Array Nat` of size 10,000 and cloning it per probe is
exponentially faster than rebuilding HashMaps.


### 3. Global Memory Bloat from Witnesses (Critical Memory Leak)
In our recent addition, `buildWitnesses` mutates the shared `GlobalDAG` to intern the primed variables ($a'$, $r'$) and the witness coupling
expressions.

**The Problem:** Witnesses are specific to a single probe's rewrite history. If you have $2^{10}$ probes, and each generates 5 unique witness
nodes, you are permanently injecting 5,000 dead nodes into the `GlobalDAG`. As the exponential loop progresses, hash-consing slows down because
the interning map becomes massive, filled with useless expressions from previous probes.

**The Fix:** You need a "Local DAG" or "Ephemeral DAG" layer. Witnesses should be interned into a localized state that is thrown away after the
probe is checked. Alternatively, run the exponential check loop to find the security boolean *first*, and only build the witness DAG artifacts
for the probes you specifically want to output or formally log.


### 4. $\mathcal{O}(n^2)$ Node Constructors (Time Leak)

Look at `xorInsert` and `andInsert`. They use binary search to find the index, but then call `arr.insertIdx!` or `arr.eraseIdx!`.

**The Problem:** `insertIdx!` and `eraseIdx!` shift all subsequent elements in the array memory. Because you call these inside a `foldl` over
children (in `flattenXor` and `flattenAnd`), building a node with $N$ children takes $\mathcal{O}(N^2)$ time. 

**The Fix:** For small arrays (2-4 children), this is fine. For larger flattened arrays, it is much faster to push everything to an array,
run standard `Array.qsort`, and then do a single $\mathcal{O}(N)$ pass to remove duplicates (or apply $\mathbb{F}_2$ cancellations).


### 5. Parent Array Filtering in `decrementParent` (Time/Garbage Leak)

When a node is rewritten, `decrementParent` removes the rewritten node from the parent lists of its siblings using:
`acc.parents.insert cid (((acc.parents[cid]?).getD #[]).filter (· != nodeId))`

**The Problem:** `Array.filter` allocates a brand new array every time it is called. Doing this deep within the rewrite recursion creates an
enormous amount of garbage collection pressure.

**The Fix:** Instead of reallocating arrays, consider a "lazy deletion" approach. Just keep a `HashSet NodeId` (or a flat boolean `Array Bool`
indexed by `NodeId`) of `deletedEdges` or `rewrittenNodes`. When iterating over parents later, just skip any IDs marked as deleted.


To handle exponential worst-case scenarios, the architecture needs to shift from "allocating new structures per-probe" to "mutating and resetting
pre-allocated flat arrays."
